# Q2 — 3-Environment Architecture Evolution

## Overview

This document describes how the current single-EC2 LobeChat deployment evolves into a three-environment architecture (dev, staging, prod) on AWS. The core principle driving this evolution is straightforward: as you move from dev → staging → prod, you spend more money to reduce the probability and impact of failures.

---

## Per-Environment Component Table

The stack comprises nine services. The key architectural decision is which services remain containerised and which graduate to AWS managed services. This decision hinges on whether a service is **stateful** (stores data that cannot be trivially recreated) or **stateless** (can be replaced by restarting a container).

Stateful services: Postgres (user accounts, chat history, Casdoor identity data), MinIO/S3 (uploaded files, documents), Qdrant (vector embeddings for RAG).

Stateless services: LobeChat, Casdoor (process is stateless; its data lives in Postgres), MCPHub, Hayhooks, linux-sandbox, Caddy.

| Component | Dev | Staging | Prod |
|---|---|---|---|
| **LobeChat** | Container on EC2 | Container on EC2 | Container on EC2 |
| **Casdoor** | Container on EC2 | Container on EC2 | Container on EC2 |
| **Postgres** | Container on EC2 | RDS `db.t3.micro`, single-AZ | RDS `db.t3.small`, Multi-AZ |
| **MinIO / S3** | Container (MinIO) on EC2 | S3 bucket | S3 bucket with versioning |
| **Qdrant** | Container on EC2 | Container on EC2 | Container on EC2 |
| **MCPHub** | Container on EC2 | Container on EC2 | Container on EC2 |
| **Hayhooks** | Container on EC2 | Container on EC2 | Container on EC2 |
| **linux-sandbox** | Container on EC2 | Container on EC2 | Container on EC2 |
| **LLM backend** | DeepSeek API (external) | DeepSeek API (external) | DeepSeek API (external) |
| **Reverse proxy** | Caddy (systemd) + sslip.io + Let's Encrypt | ALB + ACM | ALB + ACM + WAF |
| **Secrets** | SSM Parameter Store | Secrets Manager | Secrets Manager (with rotation) |
| **DNS** | sslip.io (free, no SLA) | Route 53 | Route 53 |
| **Monitoring** | Docker logs only | CloudWatch basic | CloudWatch alarms + SNS |

### Why migrate Postgres and MinIO but not the stateless services?

Containerised Postgres and MinIO can be backed up manually (EBS snapshots, `pg_dump`, scripted routines), but the team must design, test, monitor, and restore these backups themselves. RDS automates daily snapshots, point-in-time recovery, and Multi-AZ failover. S3 provides 11-nines durability with automatic cross-AZ replication and versioning. The operational burden of managing backups is shifted to AWS, reducing the risk of human error during a stressful recovery.

The stateless services (LobeChat, Casdoor, MCPHub, Hayhooks, linux-sandbox) carry no persistent data — restarting a container restores full functionality. There is no benefit in migrating them to managed services.

### Qdrant on EC2 — Justification

Qdrant remains on EC2 in all three environments because no AWS-managed vector database offers a drop-in replacement with equivalent API compatibility. The key consideration is that Qdrant's embeddings are **derived data**, not primary data. The source documents reside in S3 and metadata lives in RDS, so Qdrant can theoretically be rebuilt by re-embedding from those sources. This leads to two viable backup strategies:

| Approach | Snapshot frequency | RPO | RTO | When to choose |
|---|---|---|---|---|
| **Quick restore** | Every 6–12h (EBS snapshots via AWS Data Lifecycle Manager) | 6–12h | 15–30 min | Large corpus where re-embedding takes hours and costs significantly |
| **Rebuild** | Daily or pre-deployment only | 24h+ | Hours | Small corpus (e.g. a business school's document set) where re-embedding is fast and cheap |

For a European business school with a moderate document corpus, the rebuild approach is rational — re-embedding a few thousand documents may take 30 minutes and cost a few dollars in API calls. Pre-deployment EBS snapshots provide a safety net for deployment-related failures.

### Managed Services in Production (≥ 4 required)

1. **RDS for PostgreSQL** — automated backups, point-in-time recovery, Multi-AZ failover
2. **S3** — durable object storage replacing containerised MinIO, with versioning for accidental deletion recovery
3. **Route 53** — DNS with 100% availability SLA and health-check-based failover, replacing the volunteer-run sslip.io
4. **ACM** — managed TLS certificates on ALB with automatic renewal, eliminating the risk of certificate expiry edge cases
5. **Secrets Manager** — secrets storage with built-in rotation for database passwords and API keys
6. **CloudWatch** — centralised logging, metric alarms, and SNS alerting for operational visibility

## Promotion Flow

### Branching Strategy

- **Feature branches** → dev environment (developer testing)
- **`main` branch** → staging environment (integration and acceptance testing)
- **Version tags** (`v1.2.0` via `cz bump`) → production environment

### Deployment Mechanism

GitHub Actions pipelines handle deployment at each stage:

1. Developer pushes a feature branch → CI runs linting, container build, smoke tests
2. PR merges to `main` → GitHub Actions deploys to staging automatically (SSH + `docker compose pull && docker compose up -d`, or Ansible playbook)
3. Staging validated → developer runs `cz bump` to create a version tag
4. Tag push triggers production pipeline → **requires manual approval** via GitHub Actions environment protection rules before deployment proceeds
5. Pre-deployment step: RDS snapshot + Qdrant EBS snapshot taken automatically before the production deployment begins

### Configuration Management

Environment-specific configuration is **never stored in git**. Instead:

- **GitHub Actions secrets** hold CI/CD credentials (AWS access keys, SSH keys)
- **AWS Secrets Manager** stores application secrets per environment (database passwords, DeepSeek API key, Casdoor secrets, S3 credentials)
- **Per-environment variables** (domain name, RDS endpoint, S3 bucket name, Qdrant hostname) are injected by GitHub Actions or resolved dynamically at deploy time

This allows the same application code to flow through all three environments with different configurations.

### Rollback Strategy

If a production release fails:

- **Application rollback**: re-deploy the previous version tag's container images from GHCR. Old images are retained and tagged by version.
- **Data rollback**: restore RDS to the pre-deployment snapshot (point-in-time recovery). Restore Qdrant from the pre-deployment EBS snapshot. S3 versioning allows recovery of overwritten or deleted objects.

## Data Strategy

### Dev — Anonymised Synthetic Data

Dev uses synthetic data only. No real user chat histories, file uploads, or RAG documents. Personal information is replaced with fabricated equivalents generated to match production schemas. This satisfies GDPR requirements and prevents accidental exposure of real user data in development environments.

### Staging — Production-Like, Anonymised

Staging mirrors production infrastructure (RDS, S3, Qdrant on EC2) with anonymised data. Data is either generated to match production schemas or derived from production backups with personal information stripped. Staging is used for migration testing and integration validation before production deployments.

### Production — Layered Backup

- **RDS**: automated daily backups with 7-day retention + point-in-time recovery + pre-deployment snapshots
- **S3**: versioning enabled for accidental deletion recovery
- **Qdrant**: EBS snapshots via AWS Data Lifecycle Manager (frequency based on corpus size) + pre-deployment snapshots via GitHub Actions

## Trade-Off Table

| Dimension | Dev | Staging | Prod |
|---|---|---|---|
| **Reliability** | Low — single EC2, no failover, minimal backups, single point of failure | Medium — managed services (RDS, S3), but single-AZ, less monitoring | High — Multi-AZ RDS, S3 durability, ACM auto-renewal, CloudWatch alerting, approval-gated deployments |
| **Monthly cost** | Low (~$40–80) — one EC2, no managed services | Medium (~$120–200) — managed services at small tiers, single-AZ | High (~$300+) — redundancy, Multi-AZ, backup storage, monitoring, managed services |
| **Ops complexity** | Low — `docker compose up`, fast to provision and tear down | Medium — CI/CD pipelines, secrets management, environment parity to maintain | Medium-High — more infrastructure, but managed services reduce manual burden compared to fully self-hosted |
